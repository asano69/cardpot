# SSE安定化 × Resumable Pull 自己修復の統合設計

## 基本原則の確認

階層を明確に分けるのが鍵です。

- **SSE（PocketBaseのrealtime subscribe）**: 「なにか変わったかもしれない」という**トリガー**でしかない。正しさの根拠にしない。
- **Pull型差分同期**: 「カーソル以降の全変更」を取得する**正の情報源**。冪等マージで反映する。
- **接続健全性監視**: SSEというトリガー機構そのものが生きているかを確認する**補助レイヤー**。トリガーの信頼性を上げるが、正しさそのものには関与しない。

この3層は依存関係が一方向であるべきです：接続健全性 → トリガー発火 → pull実行 → マージ。逆方向の依存（pullの成功をもって接続が生きていると判断する、など）を作ると複雑になるので避けます。

---

## 1. カーソル設計（差分同期の土台）

PocketBaseには`updated`という`autodate`フィールドが各コレクションに標準である（このプロジェクトの`cards`/`pots`も同様）ので、これをカーソルの軸にできます。

- **カーソル値**: `(updated, id)`の複合値。`updated`だけだと同一タイムスタンプ内での順序保証がないため、`id`をタイブレーカーにする。
- **保存場所**: `localStorage`（このアプリはIndexedDBを使っていないので、`cardsStore`/`potsStore`と同じ粒度でシンプルに）。
- **差分取得クエリ**: `updated > {last} || (updated = {last} && id > {lastId})`をfilterに使い、`sort: "updated,id"`で取得。

### tombstone（削除）問題

PocketBaseは削除イベントをSSEでは通知しますが、**pull（`getFullList`/`getList`）には削除された行が原理的に出てこない**ので、「カーソル以降のupdated一覧」だけでは削除の取りこぼしを検知できません。ここが設計上いちばん難しい部分です。

現実的な対処は3つあり、どれを選ぶかがこの設計のコアな意思決定になります。

| 方式 | 概要 | コスト | 精度 |
|---|---|---|---|
| A. 専用tombstoneコレクション | `cards`削除時にhookで`card_tombstones`に`{id, deletedAt}`を書く | 新規コレクション+hook | 高（削除も差分取得できる） |
| B. 定期フルID照合 | 一定間隔で全件IDリストを取得し、ローカルに存在するが取得結果にないものを削除扱い | 実装コスト低 | 中（間隔分の遅延） |
| C. SSEのdeleteイベントのみに依存 | 削除はSSEでしか検知しない | 実装コスト最小 | 低（SSE取りこぼし＝永久にゴースト） |

このアプリの規模（1〜20人、1potあたり最大10万件）を考えると、**A（tombstoneコレクション）が本筋**です。理由：

- `cards`は`pot`単位で数千〜10万件になりうるので、Bの「定期フルID照合」は帯域・DB負荷的に厳しくなる。
- PocketBaseのhook（`OnRecordAfterDeleteSuccess`）は既に`ydoc.go`の`forgetRoom`で使われているパターンなので、実装の型が既存コードベースと一致する。
- tombstoneは「短期間だけ保持して掃除するログ」として設計すればテーブルは肥大化しない（例: 7日分だけ保持、cronで削除）。

Cのみだと「SSEを取り逃したら自己修復できない」という、まさに今回解決したい問題を放置することになるので不採用。Bは今回は複雑さに見合わないので、フェーズ2以降の保険として位置づける程度でよいと思います。

## 2. 接続健全性レイヤー（SSE安定化）

PocketBase SDKの`subscribe()`は内部的に`EventSource`を使っており、SDK自身がある程度自動再接続しますが、以下は保証されません。

- 再接続が起きたこと自体をアプリ側が知る
- 再接続中に流れたイベントの欠落
- ブラウザタブがバックグラウンドになったあとの復帰時の健全性

### 状態機械で表現する

```
disconnected → connecting → connected → (degraded) → reconnecting → connected
```

- **connected**: SDKの接続コールバック（PocketBaseの`subscribe`はコールバック登録時に接続確認ができる、または`pb.realtime.OnDisconnect`的なフックがあれば利用）に加えて、**アプリ独自のハートビート**で確認する。PocketBase自体にはハートビートイベントの標準はないので、「N秒以上イベントが来なくても異常ではない」が前提になる点に注意。
- **degraded判定の実用的な方法**: PocketBaseは正確なハートビートを送らないため、「イベントが来ないから死んでいる」とは判定できない。代わりに以下のいずれかで判定する：
  - ブラウザの`navigator.onLine`変化
  - `document.visibilitychange`でタブが復帰した瞬間
  - `EventSource.readyState`（SDKがラップしていても、内部の`eventSource`インスタンスに触れられるか要確認。触れなければSDK側の再接続イベントに頼る）
- **reconnecting → connected**: SDK側の再接続完了イベント（あれば）をトリガーに、**必ずpullを1回走らせる**。ここが2つの戦略をつなぐ最初の接点。

### 実装上の落とし所

このアプリの規模なら、複雑なハートビートプロトコルを自作するより、**「疑わしきはpullする」**という方針でシンプルにするのが「保守性重視」の方針に合います。具体的には：

- `visibilitychange`でタブがforegroundに戻ったら無条件でpull
- `online`イベントが発火したら無条件でpull
- SDKの再接続コールバックが取れるなら、それでも無条件でpull
- 上記に加えて、**一定間隔（例: 5分）の定期pullをフォールバックとして必ず入れる**（これが「SSEが本当に死んでいても最終的には気づける」という保証になる）

つまり「SSE切断を精密に検知する」ことにコストをかけすぎず、「怪しいタイミング全部でpullする」＋「定期pullで下限を保証する」という設計にすると、複雑さと信頼性のバランスが良いです。

## 3. 統合：いつpullを起動するか

pull起動のトリガーを一覧化すると、これが設計の中心になります。

| トリガー | 目的 |
|---|---|
| アプリ起動時 | 初期状態を正しくする（既存の`loadAllCards`に相当） |
| SSEで実際にイベントを受信した直後 | 通常運用（今のstoreがやっていること） |
| SSE再接続検知時 | 切断中に取り逃した分の穴埋め |
| タブがforeground復帰時 | 長時間バックグラウンドでの取りこぼし対策 |
| `online`復帰時 | ネットワーク断からの復帰 |
| 定期タイマー（例: 5分） | 上記すべてを取り逃した場合の最終防衛線 |

重要なのは、**これらすべてが同じ「resumable pull」関数を呼ぶだけ**という点です。SSEのイベントハンドラ自体は「何も信用せずpullを呼ぶトリガー」に格下げしてもよいくらいで、実際にはパフォーマンスのため「SSEで来たイベントは楽観的にマージしつつ、上記トリガーでは必ずカーソルベースのpullで裏取りする」という二段構えにするのが実用的です。

```
SSEイベント受信 → 楽観的マージ（今のcardsStoreの挙動、体感速度優先）
                → かつイベントに含まれるupdatedでカーソルを前進
                （ただし、これだけではpullを代替しない）

上記の「怪しいタイミング」トリガー → resumable pull実行
                                    → tombstoneも含めて差分取得
                                    → 冪等マージ
                                    → カーソル更新
```

## 4. 冪等マージの設計

既存の`cardsStore.ts`の`mergeCards`はすでに「idをキーに上書き」という冪等な設計になっているので、これはほぼそのまま使えます。追加で必要なのは：

- tombstone分の削除処理（`deleteFromStore`は既にある）
- pull結果とSSE結果が競合してもLast-Write-Wins（`updated`比較）で問題ないことの確認 — PocketBase自体のレコードは単一サーバのDBなので、クライアント間の競合はそもそも起きにくく、この点はシンプルに保てる

## 5. フェーズ分け（実装しないが、導入順序の指針として）

1. **フェーズ0**: カーソル（`updated`+`id`）を使った`fetchSince(cursor)`関数を作る。tombstoneコレクションはまだ作らず、削除はSSEのみに依存（現状維持）。
2. **フェーズ1**: 起動時pull・visibilitychange・online復帰・定期タイマーの4トリガーを実装し、全部同じ`fetchSince`を呼ぶようにする。ここまでで「取りこぼしても数分以内に自己修復する」状態になる。
3. **フェーズ2**: tombstoneコレクション＋hookを追加し、削除の取りこぼしも解消する。
4. **フェーズ3（任意）**: 接続状態の状態機械をUIに露出する（Footer等に「オフライン」表示など）。これはこのアプリの「1〜20人の小規模チーム」という前提だと優先度は低め。

---

## まとめ：責務の切り分け

- **SSE安定化戦略**は「pullを起動するきっかけを増やす／早める」役割に限定する。SSE自体の正確性を追求しない。
- **Resumable pull**が唯一の「正しさ」の根拠であり、カーソル＋tombstoneで完結させる。
- 両者は「pullを呼ぶトリガー一覧」という1点でのみ結合させ、それ以外は疎結合に保つ。これにより、将来SSEをやめてポーリングだけにする、あるいは逆にWebSocketに変えるといった変更があっても、pull側のロジックには影響しない設計になります。
